## End-to-end integration

`tests/test_services.py` runs **12 checks against a live stack**, talking to the
five services over HTTP exactly as a client would, so it exercises the images,
the mounts, the authentication and the inter-service call — none of which a unit
test touches.

It is built to catch three things that would each leave a stack looking healthy
while being useless:

- **Services that answer with nothing.** A missing mount makes every endpoint
  return an empty list, which looks like a valid response. The tests assert
  against the *committed numbers*, so an empty mount fails loudly.
- **Authentication that is not enforced.** Every protected route is called
  without a token and must return 401.
- **A breached read-only boundary.** The analytics service's own OpenAPI schema
  is read and checked for mutating routes.

Result: **12/12**, against both the Compose stack and the Kubernetes deployment.

## Citation verification

`src/verify_citations.py` resolves every identifier against the registry that
issued it and **compares the registered title against the cited one**. A DOI that
resolves is not the same as a DOI that resolves to the work you meant; only the
second is worth anything.

Publisher pages (IEEE Xplore, ScienceDirect) block automated fetching, so DOIs
are checked against CrossRef — the registration agency's own record, which is
what a DOI actually is — and preprints against the arXiv API. JMLR assigns no
DOIs, so its one entry is verified against the journal's own article page.

Result: **9 verified, 2 software without an identifier, 0 unresolved.**

**The check earned its place immediately.** The Stable-Baselines3 entry was first
given a guessed arXiv identifier, which resolved to *"Audio-Visual Scene-Aware
Dialog and Reasoning using Audio-Visual Transformers"* — a real paper, entirely
unrelated. Had the bibliography been assembled by hand it would have shipped with
a citation pointing at the wrong work. It is now verified against JMLR 22(268),
and the incident is recorded in the citation file rather than quietly corrected.

The two software entries — sumo-rl and Ultralytics — have no DOI and no
accompanying paper. They are cited by repository rather than given a fabricated
identifier.

### A five-minute walkthrough

1. **The problem** — open the visualiser on fixed-time. At t = 20:00 there are
   116 vehicles stopped.
2. **The result** — press `c` for side-by-side. Same traffic, same instant: RL
   has 13 stopped. This is the whole project in one screen.
3. **The honesty** — the result card names the Week 5 failure and points at the
   report. Open `BENCHMARK_REPORT.md` at "Where RL does not win".
4. **The negative finding** — five variants, byte-identical metrics, 100%
   decision agreement; then the same effect again in Week 9's federated result.
   This is the most interesting thing the project found.
5. **The platform** — the dashboard, every panel served live; then Grafana.

That sequence answers the DoD's three questions in order: what was built, why
each de-risking choice was made, and what the benchmark proves.
